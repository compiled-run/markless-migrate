# CI process

CI is green on `main` or the next push to `main` is the fix. A failing check is classified before anything is changed: a regression, environment or config drift, a failure that was already there, or nondeterminism. Nondeterminism gets its cause fixed (awaited readiness, random ports, no wall-clock races). A check is never made to pass by skipping it, loosening it or retrying it.

## Browsers

`check` measures the slow network in Chromium, Firefox and WebKit by default. Every workflow job that runs `check` installs all three (`.github/actions/setup` with `browsers: chromium firefox webkit`), and with `CI` set, `check` exits 2 before checking anything if one of them is missing. `--slow-network-browser` narrows the browsers on purpose.

## Quarantine

A nondeterministic failure whose cause is not fixed yet is listed here with its evidence, an owner and an expiry date at most two weeks out. The test keeps running. A red run of a listed test may be rerun once, and the rerun is noted on the PR. A listed failure in any other test, or a second red on rerun, is treated as a real failure. On the expiry date the entry is either fixed or reviewed and renewed with what was learned.

## Runners

The org runs at most 60 jobs at once, shared by every repository, and queued jobs start roughly in the order they were queued. On 2026-10-28 at 01:25Z, ten pull request runs here (29 jobs each) held all 60, with 364 more queued, and Markless's merge queue sat with 3 jobs running and 179 waiting. So:

Between 2026-10-28 and 2026-10-31 the org was at 55 or more of its 60 runners 42% of the time, and this repository's pull request CI was 40% of all runner time; the checker's two mutation suites, next-app (6 shards) and vite-site (4 shards), were 60% of that. So each suite runs here:

| Suite | Pull request | Merge queue | Push to `main` |
| --- | --- | --- | --- |
| Typecheck, unit tests (5 shards) | yes | yes | only if the merge queue did not test this commit |
| e2e quick, pages, networks (Chromium, Firefox, WebKit), shadcn, parity | yes, unless only `examples/`, `deploy/`, `docs/` or Markdown changed | yes | only if the merge queue did not test this commit |
| e2e next-app (6 shards), vite-site (4 shards), corpus (4 shards) | no | yes | only if the merge queue did not test this commit |
| Check budget (`scripts/check-budget.ts`: the checker's own time and peak memory on one fixed page, base against head on one runner) | yes, unless only `examples/`, `deploy/`, `docs/` or Markdown changed | yes | no |

- A pull request's CI holds at most 11 runners (Typecheck, five unit shards, five e2e jobs, the check budget) for about 15 minutes; the check budget measures the checker twice, about 6 minutes each on a Mac, so expect it to run longest.
- The merge queue (ruleset "main protection", on since 2026-10-31) squashes, requires every check green, gives a group 240 minutes, builds up to 2 groups at once, merges up to 10 pull requests per group and waits 1 minute to fill one. Merge with `gh pr merge <n> --squash`, which adds the pull request to the queue.
- The merge queue tests the exact commit `main` will become, with every suite, before it lands. A push to `main` whose commit passed the merge queue at that SHA does not run them again; the Changes job links the queue's run. A push that did not come through the queue runs everything.
- No e2e suite reads `examples/`, `deploy/` or `docs/`, so a pull request that only touches those, or Markdown, skips the e2e jobs.
- Every push to `main` and every merge queue group gets a run of its own that the next merge does not cancel. In one shared group, merges a few minutes apart cancelled each waiting run, and `main` went hours without a finished one.
- At most two full-site runs go at once across `convert.yml`, `check.yml`, `pipeline.yml`, `probe-dead-controls.yml` and `probe-measure.yml`. A run is full-site when it names 50 routes or more, or no route list (every page). Its first job, `full-site gate` (`scripts/full-site-gate.ts`), waits on one runner until fewer than two full-site runs are ahead of it: every admitted one, and every older one still waiting. So runs start oldest first and none is cancelled. A gate still waiting after 330 minutes fails. `gh run rerun <id> --failed` then waits again in the same place, because a run keeps its creation time. Subset runs, and check.yml when the pipeline calls it, pass straight through. On 2026-10-31 parallel full-site dispatches had one convert with 21 of 24 shards queued.
- A pipeline or check run dispatched with `-f priority=deploy` (the night's deploy run) skips the full-site gate and does not count against its two slots.
- Not on today: a paid larger-runner pool for capture shards during proof-heavy stretches. A full-site capture is about 1,400 to 1,500 runner-minutes, about $9 on a 2-core larger runner at $0.006/min. If it is ever wanted, capture's `runs-on` would read a repository variable (`${{ vars.CAPTURE_RUNNER || 'ubuntu-24.04' }}`), so it is switched on and off without a code change.
- Every job runs on `ubuntu-24.04`, not `ubuntu-latest`. On 2026-11-05 `ubuntu-latest` began handing out Ubuntu 26.04 runners; they restored the browsers cached on 24.04, WebKit did not start on them, and every corpus check stalled until its 150-minute limit (run 41998076432). The runner's OS is an input to every verdict, so it moves only in a change of its own, with the browser cache keys moved with it.
- `check.yml` and `convert.yml` run at most 10 shards at once. The one exception is a deploy run: `check.yml` (or the pipeline's `check-max-parallel`) with `priority=deploy` may run all 24 shards at once, because a full shadcn check at 10 took 7 to 9 hours and the night's deploy waits on it (approved by the PM on 2026-10-31, while runner waits were low). `check.yml` no longer runs on pull requests; try a change to it with `gh workflow run check.yml --ref <branch>`.

## Convert budget

The convert budget's 120 s of CPU time is CPU time at the bound's speed: the runner #656's tree read 92 s on, about 1.3 times that figure. GitHub gives this job runners whose speed differs by about 1.6 times (the same tree read 79 s on an AMD EPYC 9V45 and 125 s on an EPYC 7763), so the job converts main, then the change, then main again on one runner, and judges the change's reading over the lower of main's, times main's anchor (`ANCHOR` in `scripts/convert-budget.ts`: main's CPU time at the bound's speed, measured against #656's tree on one machine). A change that moves that figure by more than the anchor's margin sets the anchor to it in the same change, and one over the bound or off its anchor is read a second time, the lower reading judged, so no single slow reading passes or fails a change.

## Unit shards

The unit job runs `test/*.test.ts` in 5 shards. Each file's shard is its own entry in `scripts/unit-shards.json`, with its slowest measured time on a runner, and `node scripts/unit-shards.ts run <k>/5` runs shard k's files longest first, 3 at a time (node's default on the 4-CPU runner, where the times were measured). Adding, renaming or removing a file never moves another file, so a pull request's unit shards change only by its own files.

Until 2026-11-19 the job used node's `--test-shard`, which deals the sorted file list by position: one new file moved every later file to the next shard. On #721 (merge queue run 44496734135) that put `checker-noise`, `interaction-quality`, `memory`, `route-coverage` and `slow-click` in one shard, which passed the 1200 s watchdog although nothing it ran had changed.

- Adding a test file: add its line to `scripts/unit-shards.json`, `"test/<name>.test.ts": {"shard":<k>,"seconds":<s>}`. Without it `test/unit-shards.test.ts` fails, and its message gives the line with the shard to use (the one with the least modelled time, where the file runs until then); `<s>` is the file's time on CI, which the unit job prints for every file at the end of its log. Renaming a file renames its key; removing a file removes its line.
- The budget is 960 s per shard, 80% of the 1200 s watchdog: the shard's files, at their slowest measured times, run longest first on 3 lanes. Over 9 runs that model was within 15% of each shard's real time (it once read 564 s for a shard that took 648 s), and a file's own time varied by up to 1.6 times between runs (`memory`, 268 to 424 s), which the slowest times already carry. The longest file, `checker-noise` (782 to 848 s), sets the slowest shard on its own.
- Each `run` prints every file's time beside its listed one; when files grow, update their seconds from those lines. `node scripts/unit-shards.ts pack 5` deals every file afresh by its seconds (it moves files, so do it only to rebalance, in a change of its own).

## Upstream suites

`.github/workflows/upstream-suites.yml` runs the libraries' own browser tests against `parts/` when `parts/`, `src/convert/` or `test/upstream/` change: cmdk's and vaul's Playwright suites, Radix's Cypress suite and react-day-picker's keyboard tests, each against its test app as the converter turns it into a Markless app (`test/upstream/libraries.ts` pins each to the version ui.shadcn.com uses). A test counts only when it passes on the library itself through the same adapter, twice. `test/upstream/known.json` lists each admitted test that fails on the port, with its class (part, convert, shape or adapter) and why; the job is red when an admitted test fails that is not listed, or a listed one passes (take it off the list). One run takes about 25 minutes on its four runners, most of it Radix's 20-second Cypress timeouts.

## Slow-network verdicts

`test/e2e/slow-network.test.ts` ("a resource only Firefox requests ...") compares a page against an identical copy in 9 cells (3 browsers, 3 gated times), 4 runs a side. It went red 7 times between 2026-10-21 and 2026-10-28 (CI runs 40592884982, 40576060649, 40447488442, 40603280988, 40636265801, and the runs of main b37f5234, #365 and #367), each a 10 to 20 ms gap: with 4 runs a side the one-sided Mann-Whitney test's two smallest p values, 0.014 and 0.029, are both under 0.05, so one slow run made an identical page significant. `check` now also needs the median to be later by at least max(33 ms, 5% of the old median, the noise band, the instrument's step); `test/slow-network-verdicts.test.ts` deals the measured runs of two such pages into every 4-against-4 split (140) and finds none red, and every split red with 100 ms added to the new side. The test came off the quarantine list after 10 of 10 green runs of it on a Mac at load average 7 to 11 (2026-10-28) and a green pull request run on CI. It went red once more on #455 (CI run 41136076115: Firefox Regular 3G first frame 0.15 s later at p = 0.029). The cause was the rule, not the timing: each cell had its own 0.05, so a route's 9 cells went red together about 1 time in 5 on identical pages. Since then a route's cells share one significance (Holm's step-down per gated time, `routeVerdicts` in `src/check/slow-network-verdicts.ts`). Whether identical pages stay green is a rate, so it is asserted where it is exact: a seeded simulation in `test/slow-network-verdicts.test.ts` runs the product's verdict code over 1,000 routes of 9 cells and finds 2.9% red on identical pages and 99.8% red with the first frame 0.3 s later in one cell (22.1% red on identical pages under the old rule). The live test now checks the wiring only: Firefox alone fetches the resource, and its cell is red (missed about 0.04% of runs even if 1 run in 20 stalls a second).

## Bug corpus

Every bug the owner found by hand in the ui.shadcn.com port is in `deploy/shadcn-ui/corpus/bugs.json`, with its route, the gesture that shows it and the finding check must report for it. Two gates keep check reporting them:

- `test/e2e/corpus.test.ts` puts each bug back into a micro-site page built like the original's widget (`test/corpus/site.ts`) and runs the check CLI on it, as one page of a site larger than 20 pages, so the page is not its template's representative. It runs in the merge queue and on `main` (the mutation job). A case is caught only by a finding of its own class that names its control; a control the run never used names nothing. Cases listed as pending in the test are not caught yet and say which work takes them.
- `.github/workflows/corpus.yml` checks the real routes on the kept port builds that still have the bugs (release assets, never redeployed), against the original built from source, on every push to `main` that changes the checker. It calls `check.yml` once per build on that build's bug routes (`deploy/shadcn-ui/corpus/targets-<build>.json`), so each route is checked as a site's run checks it, a route longer than its timeout sliced. `scripts/corpus.ts verify` fails the run when a bug's route was checked and no finding names it, or when the route could not be checked.

A bug marked `pending` in `bugs.json` is listed by verify and does not fail it. Each pending bug has an owner and an expiry at most two weeks out; on the expiry date it is either caught or reviewed and renewed with what was learned.

| Bug | Why it is not caught yet | Owner | Expires |

A new hand-found bug goes into both: its route and build in `bugs.json`, and a case in `site.ts` that is red on the checker before the fix that catches it.

## Caches

The repository's Actions caches share one 10 GB limit, and a cache saved by a pull request is visible to that pull request alone. On 2026-10-27 the caches stood at 10.5 GB, five of them 1.4 GB copies of the same old-site build saved from pull requests, so GitHub evicted entries main's runs had saved and jobs went back to the runners' apt mirror: one slow-network job spent 12 of its 16 minutes downloading 119 MB of browser system packages at 165 kB/s. The Playwright browsers and their system packages (`.github/actions/setup`) are therefore saved from `main` only, and pull requests restore main's entries.

A browser set with no cache of its own restores a cached set that holds all of its browsers and more (`scripts/browser-cache-sets.ts`, fewest extra browsers first; a set missing one of its browsers never qualifies), so `chromium webkit` restores `chromium firefox webkit`. Playwright then finds every browser it was asked for already there and downloads nothing, and apt still refreshes its package lists from the mirror but downloads only packages updated since that cache was saved. What was restored from a larger set is never saved under the smaller set's key, so a later exact hit never carries browsers that set did not ask for.

When the browsers' system packages do go to the mirror, each mirror in the runner's `/etc/apt/apt-mirrors.txt` (Azure's, then `archive.ubuntu.com`, then `security.ubuntu.com`, which both serve the whole archive) gets one attempt of at most 3 minutes (`scripts/apt-mirror-fallback.ts`). A stall or a failure (an `apt-get update` index with the wrong size while a mirror syncs counts as one) drops that mirror from the list, routes any source that read `security.ubuntu.com` directly through the list too, and the install goes on from the next one, with a warning naming the mirror that stalled and a line naming the one that worked; only when every mirror has failed does the job fail, after at most 4 attempts. Before the first attempt the setup logs apt's source files and checks that they configure at least one repository (whether or not its package lists are downloaded yet); if they configure none the job fails at once, printing each file's text and modification time, since no mirror can help. A source file is removed only when every source in it is `packages.microsoft.com`, which the browsers' packages do not need and which has failed `apt-get update` with 403s; nothing is requested from it first, and a security reroute that leaves apt reading nothing is put back. On 2026-11-19 at 06:40Z the Azure mirror stalled and every job installing then failed at the 3-minute cap, ejecting two correct pull requests (#720, #721) from the merge queue.

## Secrets

`SHADCN_BYPASS` is the Vercel protection bypass for the shadcn-ui port's preview deployments. Only workflows that run on `workflow_dispatch` read it (today the dead-control probe, `.github/workflows/probe-dead-controls.yml`), never one that runs on `push` or `pull_request`, so a fork's run cannot read it. It is sent only as the `x-vercel-protection-bypass` header on requests to the port's host. GitHub masks it in logs, and no step prints it. It was set on 2026-10-28 from the bypass file the shadcn workers use. To rotate it, regenerate the bypass in the Vercel project and run `gh secret set SHADCN_BYPASS < <file>`.
